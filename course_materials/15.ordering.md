# Ordering

Learning goals:
  * Two roles of synchronization
    * mutual exclusion: two threads must not run some code at once
    * ordering: a thread must wait until another has done something
  * Build a bounded blocking queue
    * wait by spinning, or wait by sleeping on a condition variable
    * `wait()` and `notifyAll()`: release the lock and sleep as one step
    * test the condition in a `while`, never an `if`
    * `notify()` can wake the wrong thread; two conditions fix it
  * Use the library's ordering tools, and name what each one waits for
    * `BlockingQueue`: producer–consumer
    * `CyclicBarrier`: every thread finishes a step before any starts the next
    * `CountDownLatch`: something has happened N times
    * `Future`: the result of one task
  * Recognize a deadlock, and prevent it by taking locks in one order

## Where this picks up

  * Lecture 14: a race on a shared counter, and the ways to make it
    correct: locks, atomics, not sharing
  * all of them give **mutual exclusion**: the increments happen one at a
    time, in *some* order, and any order is fine
  * many programs need more: one thread can't go on until another has done
    something. That is **ordering**
  * we have used ordering before
    * `join()` and the end of a try-with-resources pool: wait for the
      threads to finish
    * `cilk_sync`: wait for the spawned calls
    * the end of an OpenMP parallel region: in Lecture 12's prefix sum, pass
      2 can't start until every thread has finished pass 1

## Producers and consumers

  * the most common pattern for threads that hand work to each other
    * **producers** make items: read requests, parse files, find tasks
    * **consumers** process them
    * a queue between them, so neither has to wait for the other item by item
  * a **bounded** queue has a fixed capacity, so a fast producer can't fill
    memory
  * two rules, and both are ordering, not mutual exclusion:
    * `take()` on an empty queue must wait until some thread puts
    * `put()` on a full queue must wait until some thread takes
  * a thread pool is built on one: `submit()` puts a task, and each pool
    thread loops on `take()`

The queue in every example is a circular array: `items[head]` is the oldest
item, and the next `put` goes `count` slots after it. Every access to `head`,
`count` and `items` is inside the lock, so mutual exclusion is already
handled. The question is how to wait.

## Waiting by spinning

  * code: [SpinQueue.java](../examples/ordering/SpinQueue.java)

    ```java
    long take() {
        while (true) {
            synchronized (this) {
                if (count > 0) { ...take the item...; return x; }
            }                       // empty: let go of the lock, try again
            Thread.onSpinWait();
        }
    }
    ```

  * correct: the test and the update are in the same critical section
  * it must let go of the lock between tries, or no producer could ever
    get in to put
  * but a waiting thread never stops: it keeps a core busy doing nothing,
    and keeps taking the lock the producer needs
  

## Condition variables: wait and notify

Sleep until the queue changes, and be woken by the thread that
changes it.

  * code: [MonitorQueue.java](../examples/ordering/MonitorQueue.java)

    ```java
    synchronized long take() throws InterruptedException {
        while (count == 0)          // empty: wait for a put
            wait();
        long x = items[head];
        head = (head + 1) % items.length;
        count--;
        notifyAll();                // wake any thread waiting to put
        return x;
    }
    ```

  * every Java object has a **wait set** next to its mutex; together they
    are a **monitor**
  * `wait()`, called while holding the object's mutex:
    1. releases the mutex and goes to sleep, as **one step**
    2. sleeps until another thread calls `notifyAll()` on the object
    3. takes the mutex back before it returns
  * `notifyAll()` wakes every thread in the wait set; each then competes for
    the mutex, and gets it one at a time
  * a **condition variable** is this pair of operations, whatever the
    language calls it
  * why release and sleep must be one step: if `take()` let go of the lock,
    then went to sleep, a producer could put an item and call `notifyAll()`
    in between, while nobody is asleep yet. The consumer would then sleep
    with an item in the queue: a **lost wakeup**. Java makes calling `wait()`
    without holding the mutex an error for the same reason
  * `put()` is the mirror image: `while (count == items.length) wait();`,
    then put, then `notifyAll()`
  * one wait set holds both kinds of waiting thread: consumers waiting for an
    item, producers waiting for room

![A bounded queue with capacity 4, in three steps. 1: the queue is empty and consumers C1 and C2 are asleep in the wait set after calling wait(); producer P calls put(17). 2: P holds the mutex, writes 17 into slot 0, and calls notifyAll(), waking C1 and C2, which now need the mutex. 3: C1 gets the mutex and takes 17, leaving count 0; C2 gets the mutex later, re-tests count == 0, and waits again](images/bounded_queue_wait.svg)

## Why `while`, not `if`

  * code: [IfQueue.java](../examples/ordering/IfQueue.java) — MonitorQueue
    with `if (count == 0) wait();`
  * a producer puts one item and calls `notifyAll()`: all four waiting
    consumers wake
  * the first to get the mutex takes the item; the others get the mutex one
    after another and, without testing again, take from an empty queue
  * on an M5 it fails in milliseconds: `count` goes negative and the array
    index with it (`ArrayIndexOutOfBoundsException: Index -2`), or a
    consumer takes an old item twice and the sum is wrong
  * when `wait()` returns, the condition was true *at some point*, not now:
    between the notify and the moment this thread gets the mutex, any other
    thread may have run
  * Java also allows a **spurious wakeup**: `wait()` may return when nobody
    called notify
  * so the rule has no exceptions: **wait in a loop that re-tests the
    condition**

## Why `notifyAll`, not `notify`

  * `notify()` wakes just *one* thread from the wait set, and you can't
    choose which
  * code: [NotifyQueue.java](../examples/ordering/NotifyQueue.java) —
    MonitorQueue with `notify()`
  * with capacity 1, it hung on every run on an M5:
    1. a consumer takes the item and calls `notify()`, meaning to wake a
       producer waiting for room
    2. it wakes another consumer instead; that consumer finds the queue
       empty and waits again
    3. the producers are never woken; every thread is now asleep, each
       waiting for one of the others
  * the same lost wakeup as before, from a different cause; with capacity 4
    it usually finishes, but the bug is still there
  * `notifyAll()` is always safe in this queue: every waiter wakes,
    re-tests, and the ones that can't proceed go back to sleep
  * but that is wasteful: one item arrives, and every waiting thread wakes,
    takes the mutex in turn, and almost all of them sleep again

## Two conditions: wake the right thread

  * code: [ConditionQueue.java](../examples/ordering/ConditionQueue.java)
  * a `ReentrantLock` (Lecture 14) can make as many condition variables as
    you need, each with its own waiting threads:

    ```java
    final ReentrantLock lock = new ReentrantLock();
    final Condition notFull  = lock.newCondition();   // producers wait here
    final Condition notEmpty = lock.newCondition();   // consumers wait here

    long take() throws InterruptedException {
        lock.lock();
        try {
            while (count == 0)
                notEmpty.await();
            ...take the item...
            notFull.signal();       // room for one more: wake one producer
            return x;
        } finally {
            lock.unlock();
        }
    }
    ```

  * `await()` and `signal()` are `wait()` and `notify()` for one condition
  * each `take()` makes room for exactly one item, so it wakes exactly one
    producer; each `put()` wakes exactly one consumer
  * `signal()` is now safe: only the right kind of thread is waiting on each
    condition
  * still `while`, not `if`: the woken thread competes for the lock, and may
    lose the item to a thread that arrived without waiting

## Java built-in Blocking Queue

  * code: [LibraryQueue.java](../examples/ordering/LibraryQueue.java)
  * `java.util.concurrent.BlockingQueue`, with `put()` and `take()`:
    * `ArrayBlockingQueue`: a circular array, one lock, `notFull` and
      `notEmpty`; ConditionQueue is a small version of it
    * `LinkedBlockingQueue`: a linked list with **two locks**, one for each
      end, so a `put` and a `take` don't wait for each other unless the queue
      is empty or full
  * also `offer()` and `poll()`, which give up instead of waiting, or wait
    only until a timeout
  * write your own to understand it, then use the library's

## What each queue costs

  * code: [QueueBench.java](../examples/ordering/QueueBench.java) — the five
    correct queues, 1 producer–consumer pair up to one thread per core, ns
    per item
  * two capacities, two different questions:
    * capacity 1024: producers and consumers rarely wait, and the cost is
      mostly the lock
    * capacity 1: every item is a handoff from one thread to another, like
      the `pause` and `spin` pingpong of Lecture 13, plus a sleep and a
      wakeup whenever a thread has to wait
  * results: [results.M5.md](../examples/ordering/results.M5.md), ns per
    item on an Apple M5, 1 to 5 pairs (up to 10 threads, one per core)

    | ns per item, 5 pairs | spin | monitor | condition | array | linked |
    |---|---:|---:|---:|---:|---:|
    | capacity 1024 | 300 | 148 | 29 | 31 | 40 |
    | capacity 1 | 377 | 6,953 | 4,592 | 4,771 | 4,770 |

  * sleeping costs about 4 µs per item: with capacity 1, every item wakes a
    sleeping thread through the OS, and every queue that sleeps costs 4–7 µs
  * spinning wins when there are cores to spare: the spin queue's handoff is
    a cache-line transfer, about 370 ns, ten times faster. With more threads
    than cores, a spinner would take the core its partner needs (not tested
    here)
  * spinning loses when there is little to wait for: with capacity 1024, every
    spinner hammers the queue's lock, and the spin queue is the slowest
  * `notifyAll` costs more as threads are added: with capacity 1 the monitor
    queue goes from 4.0 µs with 1 pair to 7.0 µs with 5, while the queues that
    `signal()` one thread stay at 4–4.6 µs
  * with a big queue, the cost is the lock: `synchronized` 130–155 ns per
    item, `ReentrantLock` 19–37 ns, the same gap as in Lecture 14
  * two locks didn't help: `LinkedBlockingQueue` allocates a node per item,
    and is slower than `ArrayBlockingQueue` here

## Other ways to wait

Each of these packages one pattern of waiting, built from a lock and condition
variables, so you don't have to write the loop.

### Barriers

![A timeline of a CyclicBarrier with 4 threads. Step 1 takes a different time in each thread; threads that finish early wait at the barrier until T2, the last, arrives, and then all four start step 2 together. The same barrier is reused after step 2, where T3 arrives last](images/barrier.svg)

  * code: [Barrier.java](../examples/ordering/Barrier.java) — smooth an array
    in 100 steps; each thread owns a block, and the ends of its block need its
    neighbours' values from the step before
  * `CyclicBarrier(n)`: `await()` returns, in all n threads, only when the
    last one has arrived; then the barrier resets for the next step
  * its action runs once per step, after everyone arrives and before anyone
    leaves: here, it swaps the old and new arrays
  * same answer as serial, to the last bit; with `nobarrier`, threads read
    their neighbours' elements a step early or late, and the answer is wrong
  * OpenMP: `#pragma omp barrier`, and an implicit one at the end of every
    parallel region and every `omp for`

### Latches

  * `CountDownLatch(n)`: `await()` waits until `countDown()` has been called
    n times; one use only
  * the thread that counts down doesn't wait, and doesn't have to finish:
    a latch counts *events*, not threads
  * SyncBench (Lecture 14) and QueueBench use two as a starting gun: every
    thread counts down `ready` and waits on `go`, so the clock starts with all
    threads in place
  * `join()` waits for a thread to *end*; a latch waits for something to
    *happen*

**Startup: wait until everything is ready, not until it is done.** A server
starts three threads, each preparing one part, and each keeps running after
its part is ready:

```java
CountDownLatch ready = new CountDownLatch(3);
pool.submit(() -> { loadCache();  ready.countDown(); refreshCacheForever(); });
pool.submit(() -> { openDbPool(); ready.countDown(); monitorPoolForever(); });
pool.submit(() -> { readConfig(); ready.countDown(); watchConfigForever(); });
ready.await();          // all three parts are ready; no thread has finished
acceptRequests();
```

![A timeline of a CountDownLatch with count 3 at server startup. main starts three threads and waits in ready.await(). The db pool, cache and config threads each call countDown() when their part is ready, and the count goes 3, 2, 1, 0; each keeps running afterwards. When the count reaches 0, await() returns and main starts accepting requests](images/latch_startup.svg)

`join()` can't do this: these threads never finish.

### Futures

  * a **synchronous** call returns when its work is done: the caller waits
    for the answer before it can do anything else
  * an **asynchronous** call starts the work and returns at once, with a
    handle to the answer that will come later: a **future**
    * `pool.submit(task)` returns a `Future`, and a pool thread runs the task
    * `future.get()` waits for the result, or throws the exception the task
      threw
  * the point is **overlap**: start the next request while the first is
    still out, so waits that would happen one after another happen at the
    same time

A web server builds one page from three services, each with its own latency:

```java
Future<Profile> profile = pool.submit(() -> fetchProfile(user));        //  40 ms
Future<List<Item>> recs = pool.submit(() -> fetchRecommendations(user)); // 120 ms
Future<Cart> cart = pool.submit(() -> fetchCart(user));                  //  60 ms
render(profile.get(), recs.get(), cart.get());   // ~120 ms, not 220
```

![Two timelines. Synchronous: one request thread calls fetchProfile for 40 ms, fetchRecommendations for 120 ms and fetchCart for 60 ms, one after another, and renders at 220 ms. Asynchronous: the request thread submits all three at time 0, three pool threads make the calls at the same time, and the request thread waits in profile.get() and recs.get(); cart.get() returns at once. It renders at 120 ms, 100 ms sooner](images/futures_overlap.svg)

  * synchronous, the waits add up: 40 + 120 + 60 = 220 ms. Asynchronous, the
    latency is the longest call, 120 ms
  * this is not parallel computing: the pool threads spend those 120 ms
    waiting for the services, not using cores, so it would work on one core.
    It **hides latency** by overlapping waits, as an out-of-order core
    overlaps independent instructions (Lecture 3)
  * the order of the `get()` calls doesn't matter: `cart.get()` comes last,
    but the cart arrived at 60 ms, so it returns at once
  * code: [Futures.java](../examples/ordering/Futures.java) — the syntax of
    `Future` and `CompletableFuture`, on a sum split into blocks; it computes
    rather than waits, so it shows how to write futures, not the overlap
  * Cilk's spawn and sync as a value: `submit` is the spawn, `get` is the
    sync
  * the ordering comes with the data: the result is handed over, not
    shared, so there is nothing to lock
  * `CompletableFuture`: instead of waiting, say what to do when the result
    arrives (`thenApply`, `thenCombine`); the pool runs each step once its
    inputs are ready

## Deadlock

  * code: [Deadlock.java](../examples/ordering/Deadlock.java) — transfers
    between two accounts lock both accounts
    * thread A transfers x to y: lock x, then y
    * thread B transfers y to x: lock y, then x
    * A holds x, B holds y, and each waits forever for the other's: STUCK
      within 10 s on every run
  * a **deadlock**: a cycle of threads, each holding a lock and waiting for
    one that the next thread holds
  * every lock is correct on its own; the bug is in the *order* they are
    taken, and it appears only when the timing lines up
  * the fix: one global order. With `ordered`, every transfer locks the
    account with the smaller id first, so no cycle can form
  * NotifyQueue hung in the same way without a second lock: every thread
    asleep, waiting for another to wake it

## What to carry forward

  * mutual exclusion says "one at a time"; ordering says "not before"
  * a condition variable is a lock plus a place to sleep: release and sleep
    as one step, and re-test in a `while` when you wake
  * `notifyAll` is safe and wasteful; separate conditions with `signal` are
    safe and precise
  * in real code use `BlockingQueue`, `CyclicBarrier`, `CountDownLatch` and
    `Future`, and take multiple locks in one global order
